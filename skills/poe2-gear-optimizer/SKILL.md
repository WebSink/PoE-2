# PoE 2 Gear Optimizer

## Когда применять

- Есть кандидат на замену и нужно понять, лучше ли он текущего предмета.
- Нужно выбрать, какой слот даст наибольший прирост.
- Нужно проверить требования предмета и потерю резистов/ES.

Не применять для общего аудита билда (`poe2-build-analysis`) и для поиска
объявлений (`poe2-market-research`).

## Входы

- Текущий предмет из `data/characters/<name>.json`.
- Кандидат: текст предмета из игры, объявление или поля JSON.
- Подтверждённые итоговые статы персонажа (после снятия/надевания).

## Алгоритм сравнения

1. **Слот и база.** Один слот, одна база/тип. Двуручный арбалет — это один слот,
   не два оружия.
2. **Требования.** Уровень, сила/ловкость/интеллект. Если требований не хватает —
   кандидат невалиден без перекрафта/других изменений.
3. **Плоские значения:** здоровье, ES, броня, уклонение, мана, меткость.
4. **Сопротивления:** огонь/холод/молния/хаос. Считать **итог с учётом caps**,
   а не сумму модов. Отдельно показать потерю и риск уйти в минус.
5. **Атрибуты и пороги:** +STR/DEX/INT могут включать/выключать камни.
6. **Скорость передвижения.** Для кампании и маппинга — отдельный вес.
7. **Утилитарные моды:** реген, заряды флаконов, обереги, порог оглушения.
8. **Совместимость с билдом:** моды «к уровню камней ближнего боя» бесполезны
   арбалетному билду — отмечать явно.

## Инструмент

С S5.1 сравнение выполняет код, а не модель:

```bash
uv run python scripts/gear_analyze.py --slot Boots --item-json <candidate>.json
uv run python scripts/gear_analyze.py --slot Boots --item-text <copied-item>.txt
```

Отчёт содержит требования, дельты (с пометкой `engine` / `declared`), сопротивления
до и после капа, потерянные и полученные модификаторы и оценку с формулой.
Документация — `docs/gear-analyzer.md`, ограничения движка — `docs/pob2-limitations.md`.

Если полного текста предмета нет, инструмент переходит в режим `declared_only`:
часть чисел останется неизвестной — так и надо отвечать, а не додумывать.

## Правила

- Расчёт — **детерминированный**: таблица дельт, без «на глаз».
- Не смешивать старый снимок статов с новым предметом. Нужен снимок **после**
  замены, иначе результат помечается `UNVERIFIED`.
- Не придумывать цены, наличие и продавцов.
- Учитывать, что замена может уронить resist cap — это критический риск.
- Итоговый рейтинг объяснять: почему выше/ниже, что теряется.

## Выход

```markdown
## Слот: <slot>

| Параметр | Текущий | Кандидат | Дельта |
|---|---:|---:|---:|

## Итог по caps
| Сопротивление | Было | Стало | Статус |

## Вердикт
- Решение: заменить / не заменять / нужен снимок после примерки
- Причина: ...
- Риски: ...
- Как проверить: ...
```

## Инструменты

- Детерминированные скрипты/таблицы; JSON-профиль.
- `pob-mcp`: `equip_item_raw`, `get_stats`, `compare_builds` — если есть
  PoB-экспорт билда.
- Без торговых API и скраперов.
