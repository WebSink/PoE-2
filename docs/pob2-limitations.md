# Ограничения PoB2 при анализе экипировки

Список собран по фактам, проверенным на локальной установке PoB2 `0.23.1`
(данные дерева `0_5`) через `pob-mcp`. Каждый пункт — либо измеренное поведение,
либо явное отсутствие данных, а не предположение.

## 1. Движок не проверяет требования предмета

`equip_item_raw` надевает предмет с `LevelReq: 60` на персонажа 46 уровня и
применяет его модификаторы (проверено: `+500 to maximum Life` дало жизнь
947 → 1426). То есть PoB2 считает статы для вещи, которую нельзя носить.

Следствие: проверка уровня и силы/ловкости/интеллекта выполняется анализатором
до расчёта. Для предмета, который персонаж не может надеть, движок не
запускается вовсе — иначе отчёт показал бы «улучшение» от недоступной вещи.

## 2. Требования атрибутов зависят от базового типа

Строка `Requires: Level N, X Str` приходит только в полном тексте предмета. Без
неё требования атрибутов неизвестны: анализатор ставит статус `unknown`, а не
«выполнено». То же касается локальной защиты: `Armour:`/`Energy Shield:` — часть
текста, а не модификатор.

## 3. Каскад атрибутов известен только движку

`ReqStr`/`ReqDex`/`ReqInt` агрегируют требования **всех** надетых предметов и
камней. Без движка проверить «не сломает ли замена другой предмет» невозможно —
в отчёте появляется `unknown` с пояснением «нужен расчёт движка».

## 4. Разовый урон и DPS — разные величины

`TotalDPS` основного умения — не то же самое, что разовый урон, и отображаемый
в игре DPS других умений несопоставим напрямую. В отчёт идёт только `TotalDPS`
и `FullDPS` основного умения; групповой DPS требует отдельного прохода с
`set_main_skill` по каждой группе камней и в S5.1 не реализован.

## 5. Числа действительны только для конфигурации

Импорт приходит с эндгейм-дефолтами (`resistancePenalty = -60`,
`enemyLevel = 82`, `enemyArmour = 8063`, `enemyIsBoss = Pinnacle`). Для кампании
акта III анализатор выставляет `-20`, `enemyLevel = 46`, `enemyArmour = 624`,
`enemyIsBoss = None`. Сравнивать числа, посчитанные под разными штрафами,
нельзя — поэтому в отчёте всегда указан сценарий и его конфигурация.

## 6. Сопротивления: два разных набора полей

`FireResist`/`ColdResist`/`LightningResist`/`ChaosResist` — **после** капа,
`*ResistTotal` — **до** капа (после штрафа акта). Хаос штрафом акта не
затрагивается. Если перепутать поля, «+40% огня» при закрытом огне выглядит как
улучшение. В отчёте показываются оба значения, в оценку идёт изменение после капа.

## 7. Локальная защита и глобальные модификаторы — разные вещи

`Energy Shield: 79` в шапке предмета — локальная защита; `+43 to maximum Energy
Shield` — глобальный модификатор. Движок учитывает оба, но складывать их в один
показатель нельзя. В отчёте они в разных блоках.

## 8. Движок не принимает «частично известный» предмет

`equip_item_raw` с текстом без модификаторов падает на
`Item.lua:1406: attempt to concatenate field 'baseName' (a nil value)`. Поэтому
структурированный кандидат без `raw_text` в движок не отправляется: отчёт
переходит в режим `declared_only`.

## 9. Модификаторы вне словаря остаются `UNKNOWN`

PoB2 понимает любую свою строку, но анализатор распознаёт только те, для которых
умеет считать аддитивный вклад. Всё остальное (уровни камней, условные бонусы,
«increased damage if …») сохраняется как `UNKNOWN` вместе с исходным текстом и
не участвует в арифметике. Это видимое ограничение, а не тихая потеря.

Условные и связанные модификаторы, зависящие от состояния боя, в отчёт не
подставляются: учитываются только те, чьи условия подтверждены.

## 10. Версия данных дерева фиксирована

Сейчас движок грузит tree data `0_5`. При обновлении PoB2 числа могут измениться:
версия движка и данных дерева попадают в отчёт (`engine.info`), чтобы результат
можно было воспроизвести.

## 11. Нет рыночных данных

Ни цены, ни доступности объявления, ни статуса продавца в отчёте нет и быть не
может: торговых интеграций, скраперов и недокументированных API в проекте нет.
Кандидат — это только предмет, описанный вручную.
