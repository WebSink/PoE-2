# Схема профиля персонажа

Файл схемы: [`data/schemas/character-profile.schema.json`](../data/schemas/character-profile.schema.json)
Версия схемы: **2.1.0**. Первый профиль: [`data/characters/sinkov.json`](../data/characters/sinkov.json).

## Зачем четыре уровня достоверности

Раньше профиль смешивал наблюдения из скриншотов и игровые ожидания: числа
уровня 45 стояли рядом с неподтверждённым нагрудником, а DPS выглядел как факт.
Схема 2.0.0 запрещает такое смешение структурно — у каждого утверждения ровно
один уровень достоверности, а расчётные величины физически не могут существовать
вне сценария с конфигурацией.

| Раздел | Что означает | Источник |
|---|---|---|
| `observed` | Подтверждено в игре: экран персонажа, скриншоты, клиент | `in_game_screenshot` |
| `imported` | Перенесено импортом PoB2: класс, атрибуты, предметы, камни, дерево | `pob2_import` |
| `calculated` | Посчитано движком PoB2 под конкретной конфигурацией | `pob2_engine` |
| `unverified` | Требует проверки; у каждого пункта есть `how_to_verify` | — |

`observed` и `imported` могут расходиться — это нормально и ожидаемо: наблюдение
сделано раньше. Поле `observed.superseded_by` явно указывает, какой источник
вытеснил наблюдение. Молчаливая перезапись запрещена.

## Главное правило: нет расчёта без конфигурации

DPS и EHP в PoB2 зависят от допущений о цели и штрафах. Поэтому:

```jsonc
"calculated": {
  "engine": { "version": "0.23.1", "tree_data_version": "0_5", ... },
  "scenarios": [
    {
      "id": "campaign-act3-normal",
      "captured_at": "2026-11-21",
      "config": { "resistancePenalty": -20, "enemyIsBoss": "None",
                  "enemyLevel": 46, "enemyArmour": 624, ... },
      "config_rationale": { "enemyArmour": "data/monsterArmourTable[46] = 624 ..." },
      "defence": { ... },
      "skills": [ { "name": "Voltaic Grenade", "total_dps": 259.8, "average_hit": 629.82 } ]
    }
  ]
}
```

Инварианты, которые проверяются автоматически:

1. `config` содержит `resistancePenalty`, `enemyIsBoss`, `enemyLevel`, `enemyArmour`.
2. `config_rationale` покрывает **каждый** ключ `config` — откуда взято значение.
3. У сценария есть `captured_at` и `source_id` на существующий источник.
4. Сопротивления пересчитываются из `calculated.resistance_baseline.uncapped` + штраф
   сценария и капом из `resistance_baseline.maximum` (по умолчанию 75%). Смешать `-60`
   и `-20` в одном блоке невозможно — валидатор поймает.
5. `skills[].total_dps` и `skills[].average_hit` — **разные** величины и не сравниваются
   между собой: DPS умножает удар на частоту, разовый урон — нет.

## Почему сопротивления до капа лежат в `calculated`

Экран игры и движок показывают сопротивление **после** штрафа и капа. Чтобы
проверять арифметику, нужны значения до штрафа. Для Sinkov они выведены из трёх
измеренных точек:

| Стихия | `-60` | `-20` | `0` | uncapped | Как получено |
|---|---:|---:|---:|---:|---|
| Огонь | 49 | 75 | 75 | **109** | 49 + 60 = 109; при `-20` даёт 89 → кап 75 |
| Холод | 6 | 46 | 66 | **66** | 6 + 60 |
| Молния | −5 | 35 | 55 | **55** | −5 + 60 |
| Хаос | 0 | 0 | 0 | **0** | штраф акта не влияет |

Огонь выводится однозначно: при `-60` показано 49, значит до штрафа 109; при `-20`
это 89, и кап 75 скрывает истину. Значение не «примерно», а единственное
удовлетворяющее обоим измерениям.

### Миграция 2.0.0 → 2.1.0

Раньше эти числа лежали в `imported.uncapped_resistances`, и это было ошибкой
провенанса: значения выведены из вывода движка, а не получены импортом из
аккаунта. Схема 2.1.0 переносит их в `calculated.resistance_baseline` с
собственным `source_id` вида `pob2_engine`, `captured_at`, `method`,
`penalty_reference` и массивом `evidence` — по одной записи на измеренный штраф:

```jsonc
"resistance_baseline": {
  "source_id": "pob2-engine-2026-11-21",
  "captured_at": "2026-11-21",
  "method": "get_stats при resistancePenalty = 0: FireResistTotal = 109, ...",
  "penalty_reference": 0,
  "uncapped": { "fire": 109, "cold": 66, "lightning": 55, "chaos": 0 },
  "evidence": [
    { "resistancePenalty": 0,   "total": { "fire": 109, ... }, "scenario_id": null },
    { "resistancePenalty": -20, "total": { "fire": 89, ... },  "scenario_id": "campaign-act3-normal" }
  ]
}
```

Валидатор проверяет арифметику каждой записи (`uncapped + penalty = total`), что
хаос не зависит от штрафа, что штраф в `evidence` совпадает с конфигурацией
сценария и что показанное в сценарии сопротивление равно `min(total, 75)`.

### Откуда взялся кап: `maximum` и `maximum_method`

Отдельного поля «максимум сопротивления» движок PoB2 не отдаёт. Проверено
зондом: при насыщении (`+500%` ко всем сопротивлениям) `*Resist` перестаёт
расти и равно реальному капу — для всех четырёх стихий, включая хаос, это 75.
Поэтому в профиле кап записан измеренным значением с явным способом:

```jsonc
"maximum": { "fire": 75, "cold": 75, "lightning": 75, "chaos": 75 },
"maximum_method": "насыщение в временной копии билда: +500% ко всем
  сопротивлениям, get_stats.*Resist прекращает рост и равен капу"
```

Гир-анализатор читает этот блок и не подставляет 75 молча: если `maximum`
нет, кап считается неизвестным (UNKNOWN), а значения выше 75% не попадают в
оценку как «известные».

Валидатор: `maximum` (если задан) содержит все четыре стихии, кап ≥ 75 и
`maximum_method` с текстом, иначе — ошибка.

Перевод существующих профилей:

```bash
uv run python scripts/migrate_profiles_2_0_to_2_1.py --check   # только проверка
uv run python scripts/migrate_profiles_2_0_to_2_1.py --write   # переписать файлы
```

Скрипт идемпотентен: профиль в форме 2.1.0 он не меняет.

## Резервирование духа

`imported.spirit_reservations` — не расчёт, а измерение движка по одному
источнику за раз. Поле `conditional_on` фиксирует, что `Precision I` резервирует
дух только пока активен `Herald of Ash` (это камень поддержки в его группе).

```jsonc
"spirit_reservations": {
  "maximum": 30, "free": -40, "total_reserved": 70,
  "entries": [
    { "ability": "Herald of Thunder", "group": 3, "spirit": 30, "conditional_on": null },
    { "ability": "Herald of Ash",     "group": 7, "spirit": 30, "conditional_on": null },
    { "ability": "Precision I",       "group": 7, "spirit": 10, "conditional_on": "Herald of Ash" }
  ],
  "simultaneous_combinations": [ ... ]
}
```

Проверки: `maximum − total_reserved == free`; сумма `entries[].spirit` равна
`total_reserved`; у каждой комбинации `spirit_used` пересчитывается по `entries`
с учётом `conditional_on`, а `fits` равен `spirit_used <= maximum`.

## Механические пробы

`calculated.mechanics_probes` — точечные эксперименты движка: что меняется при
снятии узла или камня. У каждой пробы есть вопрос, метод, результаты, вывод и
**ограничения**. Это место для выводов вида «движок не меняет TotalDPS при снятии
узла», которые нельзя выдать за игровой факт.

## Как добавить новый профиль

1. Получить `.xml` из PoB2 (или build code) и положить локально в `data/builds/`
   (каталог в Git не входит).
2. Снять дамп движка: `load_build` → `get_stats` / `get_tree_state` / `get_skills` /
   `get_items` / `sanity_check` / `get_config`.
3. Заполнить `sources[]`: импорт, дамп движка, статические данные PoB2, наблюдения.
4. Разнести данные по `observed` / `imported` / `calculated` / `unverified`.
5. Прогнать проверки:

```bash
uv run python scripts/validate_data.py   # схема + доменные правила
uv run pytest tests/                     # те же правила + негативные кейсы
```

## Что проверяется автоматически

| Проверка | Что ловит |
|---|---|
| Схема | пропущенные обязательные поля, лишние поля, неверные типы и enum |
| Провенанс | `source_id` без источника; ключ конфигурации без обоснования |
| Расчёты вне сценария | `dps`/`ehp`/`life` на верхнем уровне профиля |
| Сопротивления | значение не пересчитывается из `calculated.resistance_baseline` + штраф сценария |
| Провенанс сопротивлений | блок до капа оказался в `imported`; источник не `pob2_engine`; арифметика `evidence` не сходится |
| Дух | нарушенная арифметика, неверный `fits`, неизвестная способность |
| Умения сценария | ссылка на несуществующую группу камней, дубли, отрицательный урон |
| Экипировка | повторяющиеся слоты |
| Секреты | поля вида `*token*`, `*cookie*`, `*secret*`; длинные hex-строки |
| Сырой XML | встроенный текст билда или предмета |
| История | `data/characters/history/*.json` существует и разбирается |

Валидатор использует только стандартную библиотеку Python — никаких внешних
зависимостей для проверки данных. `pytest` нужен только для тестов.
